# Hybrid Healthcare LLM + Rule-Engine Fact Checker

## Project idea

This project demonstrates a hybrid AI architecture for educational healthcare decision support:

**Patient symptoms → deterministic rule engine → independent LLM draft → symbolic verification → final verified response**

The LLM is treated as a **generator**, not as the authority. A versioned knowledge base and deterministic safety rules provide an auditable verification layer.

> **Important:** This is a third-year academic prototype. It is not a real diagnostic or treatment system and must not be used for medical decisions.

## Why this is different from ordinary ChatGPT

A normal LLM can generate a plausible answer but does not automatically expose a deterministic, auditable rule set that can override unsafe output.

This project explicitly separates:

1. **Generation** — local LLM creates an explanation.
2. **Verification** — symbolic rules inspect the draft independently.
3. **Safety authority** — emergency rules can override the LLM.
4. **Auditability** — the UI exposes symptoms, rules, evidence, claims, rejection reasons and KB version.

## Core modules

- `app.py` — Streamlit UI and orchestration.
- `engine.py` — deterministic symptom scoring, red flags and symbolic verifier.
- `llm.py` — local Ollama generation layer. It deliberately does not receive the rule-engine conclusion.
- `data/knowledge_base.json` — versioned, curated pattern and safety knowledge.
- `test_engine.py` — regression tests for the verification layer.

## Main workflow

1. User selects symptoms and can add free-text notes.
2. The deterministic engine checks the symptoms against the knowledge base.
3. The local LLM independently drafts an explanation from symptoms/notes.
4. The symbolic verifier checks for:
   - unsupported certainty
   - definitive diagnosis claims
   - medication/prescription/dosing claims
   - dangerous reassurance
   - unsupported knowledge-base pattern mentions
   - emergency contradictions
5. The system either accepts the draft or replaces it with a deterministic safe response.

## Adversarial evaluation

The app contains a separate **research evaluation suite**. These cases are controlled tests, not hard-coded diagnosis logic.

The suite tests:

- Emergency contradiction
- Unsupported diagnosis
- Unsupported treatment
- Safe emergency response
- False-positive regression such as “this is not a diagnosis”

This demonstrates that the verifier can reject unsafe outputs while avoiding an earlier false-positive bug.

## Run

### 1. Create/activate virtual environment

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

### 2. Install packages

```powershell
pip install -r requirements.txt
```

### 3. Install Ollama

Install Ollama separately and download a small local model, for example:

```powershell
ollama pull llama3.2:3b
```

Start Ollama if needed:

```powershell
ollama serve
```

### 4. Run the application

```powershell
streamlit run app.py
```

Open the local Streamlit address shown in the terminal, normally `http://localhost:8501`.

## Run tests

```powershell
python test_engine.py
```

Expected output:

```text
All tests passed.
```

## Suggested project evaluation

For a stronger academic report, compare:

1. **LLM-only** — generated answer without symbolic verification.
2. **Rule-only** — deterministic pattern/safety result.
3. **Hybrid** — LLM + independent symbolic verification.

Measure:

- unsafe claim rejection rate
- false rejection rate
- emergency warning preservation
- unsupported diagnosis rejection
- treatment/dosing claim rejection
- verification latency

A useful research question is:

> **Can an independent symbolic verification layer reduce unsafe or unsupported claims generated by a local LLM in healthcare decision-support scenarios?**
